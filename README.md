# 我的计划 · 攻略与出行

基于 **Vue 3 + Element Plus + Vite** 的攻略与出行站点：主站是《艾尔登法环》，覆盖主线、支线、区域、BOSS 攻略、武器、护符、魔法、祷告、骨灰九个内容模块，外加追忆兑换、流派库、构筑器、进度总览四个工具页；`/pbz` 是与它并列的《影之刃零》攻略；摄影板块调用视觉模型做照片点评；`/travel` 是北京出行板块，给景点条件、分布图与路线规划。全部为数据驱动，无后端。

## 站点结构

站点分「门户 + 板块」两层：

**数据口径**（写在每份数据文件顶部，改数据前先看一眼）：

- 数值、机制、位置、掉落整理自 Fextralife 英文 wiki，每条详情页底部都带 `source` 链接
- 武器（29）、BOSS（55）、影之武装（24）的中文名已全部按官方对照补齐，来源分别是游侠网/游民星空/bilibili wiki 的武器图鉴、全收集与成就列表、《六十三 BOSS》拆解；新增条目照这些对照填，**不自行翻译**
- 招式名、铃铛名、道具名、地名与 NPC 名同样用中文：英文 wiki 只提供英文名，这里按字面意译，与官方中文版可能有出入；`nameEn` 字段只用于检索与核对，页面不展示
- 主线流程（`src/data/pbz/walkthrough.js`）的章节顺序、铃铛、任务与 BOSS 遭遇顺序整理自 Fextralife 的流程页（Prologue / Against the Flow / Steel and Steam / Snake's Reflection / Heartless Remnants）；该 wiki 目前只写到第三章，**第四章之后的 `steps` 留空并标 `pending`**，只列该章 BOSS 顺序与已确认门槛。中文章名来自 3DM 目录，第五到第七章目录里没标名，暂用区域名代替并标 `chapterPending`
- `scripts/check.mjs` 有一条回归检查：渲染十二个影之刃零页面后，正文里除 BOSS / Lv / wiki / Fextralife / 3DM 这类通用词与平台名外不应再出现英文
- 武器面板数值对应的等级不同（Lv1 / Lv10 / Lv30），数值旁都标了等级，跨等级不能直接比大小
- wiki 页面还是空模板的条目标为「待补」，不用推测内容填空
- 流派数据（`src/data/pbz/archetypes.js`）整理自游民星空《全流派配装推荐》13 套与《二周目推荐八套武器流派》，机制部分交叉参考 Fextralife / phantombladezero.wiki；饰品里没有可靠数值的卡面效果，统一在 `accessoryNote` 里说明，不编数字

**收藏**：

- 武器 / 影之武装 / BOSS / 流派共用一个收藏夹，存在 `localStorage` 的 `er-guide:pbz-favorites`
- 存储值带命名空间（`codex:weapons:<id>`、`codex:phantomEdges:<id>`、`boss:<id>`、`archetype:<id>`），因为几个模块的 id 可能重名
- 列表页的「只看收藏」会同步进 URL（`fav=1`），刷新与分享都能还原；详情页有收藏按钮
- 与艾尔登法环的 `er-guide:codex-favorites` 刻意分开：两个游戏的条目混在一起，导出文件会对不上版本

**全站搜索**（`Ctrl / ⌘ + K`）在影之刃零板块内同样可用，索引 `pbzWeapons` / `pbzEdges` / `pbzBosses` / `pbzArchetypes` / `pbzChapters` 五组共 131 条，匹配英文名、机制、获取位置、招式与打法关键词；搜索框的占位文案与推荐词会随板块切换。

**新增一套流派**：

1. 在 `src/data/pbz/archetypes.js` 追加一条：`core.weapons` / `core.edges` 只写图鉴里的 `name`（不是 id），名字写错会在导入时直接抛错
2. 补齐 `accessories / medicines / abilities`（名称 + 效果 + 获取），效果不确定的写进 `accessoryNote`，不要留空
3. `phases` 至少两段，`gear` 里同样用名称引用武器与影之武装；`utils/pbzArchetypes.js` 会自动解析成带链接的条目
4. 如果新增 `role` 或 `stage`，同步 `pbzArchetypeRoles` / `pbzArchetypeStages`，列表页的筛选会自动多一项
5. `npm run gen-summary` 更新 `pbzStats.archetypes`，再跑 `npm run check`

**新增一个模块**（例如「铃铛 / 地图」）的完整步骤：

1. 新增 `src/data/pbz/<module>.js`，导出条目数组与分类表（字段参考 `weapons.js`：`id / name / nameEn / category / effect / location / metrics / source`）
2. 在 `src/data/pbz/codex.js` 的 `pbzModules` 里登记，列表页与详情页自动复用 `PbzCodexView` / `PbzCodexDetailView`
3. `src/router/index.js` 加两条路由（列表 + `:id`），用 `props: { moduleKey }` 传模块 key
4. `App.vue` 的 `pbzNavGroups` 加导航项；需要统计数字时在 `scripts/gen-summary.mjs` 的 `pbzStats` 里补一项
5. `npm run check` 会自动校验新模块的 id 唯一性、分类合法性与出处完整性

## 影像分析（摄影板块）

`/photo` 的步骤：拍照（`capture="environment"`，手机直接拉起相机）/ 上传图片 → 预览 → 选择模型 → 开始分析。

分析走 OpenAI 兼容的对话接口（Gemini 官方也有同格式的 `/v1beta/openai/chat/completions`），请求体是 `messages` + `image_url`。

**接口地址 / API Key / 模型名都在页面上填**：点「选择模型」打开弹窗，填好三项并保存，`开始分析` 才会亮起。配置存在本机 `localStorage`（`er-guide:ai-settings`），刷新仍在，换浏览器需要重填；弹窗里可以「清除配置」。源码里不再内置任何 Key。

实现要点：

- 配置读写集中在 `src/composables/useAISettings.js`（单例 + 校验 + 持久化），弹窗是 `src/components/AISettingsDialog.vue`，`analyzeImage(file, settings)` 每次显式传入，不再有全局可变配置
- 提示词在 `src/config/ai.js` 的 `ANALYSIS_PROMPT`，固定四段结构（整体评价 / 具体问题 / 优化建议 / 图像编辑提示词），改口径只改这一处
- `maxTokens` 默认 4096（可用 `VITE_AI_MAX_TOKENS` 覆盖）：1500 会在「具体问题」之后耗尽预算，导致「优化建议」整段消失
- 长边超过 1600px 或体积超过 2.5MB 的图片先在 canvas 里等比压缩并转 JPEG 再发，避免网关 413；实际发送尺寸显示在结果栏
- 返回的 markdown 由 `parseAnalysis` 拆成「小节 → 段落 / 列表 / 代码块」逐块渲染，不用 `v-html`，模型输出里的标签只会当文本显示；模型漏写 `###` 时按小节名兜底识别
- 检查 `finish_reason`：被 `max_tokens` 截断或缺少某一段时，结果栏顶部会给出提示与重试，不再静默丢段
- 「图像编辑提示词」小节单独抽出，带一键复制按钮
- 超时 90 秒（`AI_CONFIG.timeoutMs`），失败时给出接口状态码与原始报错，可重试

### 请求日志

「选择模型」右边的「查看日志」跳到 `/photo/logs`（`src/views/PhotoLogsView.vue`），逐条列出最近 30 次请求：

- 请求区：方法 + 完整 URL、请求头、模型名、`max_tokens` / `temperature`、完整提示词与消息结构
- 响应区：状态码、响应头、模型原始返回（不做解析、不改写），失败时是错误类型与信息
- 成功、HTTP 错误、跨域失败、超时都会留档，所以「点了没反应」可以直接看日志

两处刻意做了裁剪：`Authorization` 只留首尾（`sk-034…393b`），图片 `data:` URL 只留前缀与体积——一次 1600px 的 base64 有两三 MB，原样存会撑爆配额也没法读。

日志存在 `localStorage`（`er-guide:ai-logs`），刷新、关浏览器都还在，最多保留最近 30 条：页面上下各有一个「清理日志」按钮，点第一次进入确认态（4 秒后自动退回），再点一次才真正删除，删完同时清掉存储键。日志内容可用「复制当前日志」导出成纯文本。

日志由 `src/utils/aiLog.js` 承担，零依赖（不 import vue），所以 Node 下的回归脚本可以直接检查脱敏与截断逻辑。

> 配置以明文存在本机浏览器，公用电脑上用完请「清除配置」。对外上线若不想让访客自带 Key，把请求挪到自己的服务端 / 代理，前端只调自己的接口。

## 旅游板块（`/travel`）

首期只做北京，面向 2027 年春节（2 月 5 日—13 日，共 9 天），全程公共交通，不含自驾。

| 页面 | 路径 | 内容 |
| --- | --- | --- |
| 板块首页 | `/travel` | SVG 景点分布图 + 必去双卡 + 七个片区 + 春节待办提示 |
| 景点库 | `/travel/spots` | 18 个景点，按片区与条件筛选，标出票价、预约、闭馆 |
| 景点详情 | `/travel/spots/:id` | 八行条件表、怎么去、现场条件、实用提示、官网出处、高德地图定位 |
| 路线规划 | `/travel/plan` | 起终点可打字搜（17 个景点 + 9 个机场 / 火车站 + 高德 POI 里的任意地址），出紧凑 / 标准 / 完整三档方案：逐天时间线、每段通勤方式与票价、门票与交通汇总、当天高德外链；另有高德实时公交方案对照 |
| 经典路线 | `/travel/routes` | 三条手排好的固定行程：中轴 3 天 / 深度 5 天 / 春节错峰 4 天 |

**数据口径**

- 18 个景点 / 7 个片区，票价与开放时间为 2026-11-16 核对快照，每条都带官网出处与核对日期
- 免费但要预约的（国家博物馆、天安门广场），条件卡里预约信息排在票价前面
- 查不到确切价格的标 `pending`，页面显示「待核实」，不填看起来合理的数字
- 长城两段（八达岭 40.36,116.02 / 慕田峪 40.43,116.57）在城区图范围外，用「方向 + 直线距离」的方向牌表示，不硬塞进城内挤坏布局
- 2027-02-08 是周一但落在春节假期内，按故宫「法定节假日除外」的规则应开放，页面标「待公告」，等 2027 年 1—2 月官方通知

**路线算法（`src/utils/travelPlanner.js`）**

不枚举全排列（18 个点是 6.4e15 种），改成「先定框架、再排顺序」：

1. **长城独占一天**，硬约束不参与打分。它和前后两天的城区行程不接续，回程后仍住市区
2. **城区按主轴排**：把起点→终点连线当主轴，片区在主轴上投影越靠前越先走，垂距越大扣分越多 —— 所以「故宫 → 颐和园」不会先绕去东边的 798
3. **装箱按当天时长**，不按片区：片区大小差太多（故宫片 6 个点塞不下一天，朝阳片只有 798 却要独占一天），真正的约束是可用时长
4. **天内顺序**用最近邻 + 2-opt，故宫固定排当天第一站（淡季 15:30 停止入馆）
5. 起点钉在第一天第一站、终点钉在最后一天最后一站；两者都不参与装箱，装完再钉，避免「终点被装到第一天中间、后面还多出一天」
6. 选了出发日期后，周一闭馆的景点自动与另一天**对调行程内容**（不交换日期，否则会出现「第 2 天 2/8、第 3 天 2/7」的日期倒流）
7. **起终点可以是交通枢纽**（机场 / 火车站 / 长城专线发车点，见 `src/data/travel/hubs.js`）：枢纽没有停留时长与门票，不进景点序列，只当「一天的起点锚」与「最后一天的终点锚」。起点是枢纽时第一天第一段算「枢纽 → 第一站」，终点是枢纽时最后一天补一段「最后一站 → 枢纽」

**通勤数据（`src/data/travel/transit.js`）**

- 城内 15 对片区通勤里，6 对按 8 号线**官方站间距**算出（北京市轨道交通《路网车站站间距信息》），分钟 = 里程/583 + 每站 30 秒 + 换乘 4 分钟 + 进出站 5 分钟
- 其余 9 对按直线距离 × 1.3 绕行系数估算，页面标「估算」，误差约 ±5 分钟；两类不混排成一个精确数字
- 票价按北京地铁里程计价（6 公里内 3 元，每加 6/10/10 公里递增）
- 长城出城四种方案并列（京张高铁 / S2 / 877 / 919），不硬算一个「最优」
- 枢纽到景点按「直线 × 1.3 绕行 ÷ 平均速度 + 进出站固定开销」估：机场线提速按 900 米/分钟、机场另加 25 分钟行李与步行，火车站加 8 分钟。全部标「估算」，机场按机场线票价（首都 25 / 大兴 35）计价，不套地铁里程票

**地图与高德**

- 分布图仍是手绘 SVG，离线可看、无 key 依赖
- 高德不嵌 JS 地图，改用 **URI 外链**（`src/utils/geo.js`）：点「在高德地图看这一天」直接在高德打开，能导航，且不需要注册 key
- 景点坐标是 WGS-84，高德是 GCJ-02，直接传会偏 300—500 米，所以做了标准转换再拼链接（`wgs84ToGcj02`）。想改成嵌真地图的话，把 key 填到 `geo.js` 的 `AMAP_JS_KEY` 即可
- **起终点支持任意地点**：`src/utils/amap.js` 直连 `restapi.amap.com`（响应头带 `Access-Control-Allow-Origin: *`，不需要后端代理），输入框联想用 `v3/place/text`，路线对照用 `v3/direction/transit/integrated`。key 存 localStorage（`myplan.amap.webkey.v2`），页面底部有输入框、「测试」和「用默认 key」三个按钮，换 key 不用重新构建
- key 必须是**「Web 服务」**平台的：JS API / Android / iOS 的 key 调 restapi 会返回 `USERKEY_PLAT_NOMATCH (10009)`，页面会把错误码翻译成「去控制台新建 Web 服务 key」这类能照做的话。代码里的默认 key 已实测可用（`place/text` 返 10000、`transit/integrated` 返 status 1），自用项目明文放前端，配额共享，别外传

**地图与排版自检**

地图是手绘 SVG（`src/components/travel/TravelMap.vue`），经纬度按 `cos(40°) ≈ 0.766` 做等距圆柱投影，比例尺 2960 px/度。城区 15 个点挤在 100×140 像素内，标签位置只能手工排（`src/data/travel/mapLabels.js`），自动避让在这个尺度上反而更容易撞。改完跑 `npm run check:map`，脚本检查越界、标签互相压住、片区名压点位。

> 本机无头浏览器不可用（Chrome 与 Edge 的 `--screenshot`、`--dump-dom` 均返回空），排版以坐标计算校验，不依赖截图。

## 功能

### 主线

- 章节时间线，标注进入条件、目标等级、武器强化档位、推荐追忆；本体、DLC 主线、DLC 可选三条链各自独立，不会从灰烬王城直接跳到幽影之地，也不会让「约定之王拉塔恩」的下一章变成可选内容

- 可选章节的依赖关系写在正文里：东线的幽影树化身掉「米凯拉的大卢恩」，大卢恩不碎魅惑不散，南线的石棺大洞最深处与谷底森林就进不去 —— 这两章的顺序不能反

- 按地表 / 据点 / 地下 / 幽影之地四层分组，区域卡片含进入方式、子区域、章节归属与关键道具

### 流派库

- 10 套成型路线，按加点主属性（力气 / 敏捷 / 智力 / 信仰 / 感应）与成型阶段（开局速成 / 中期成型 / 后期毕业）筛选，筛选条件写入 URL
- 每套都从「开局怎么起手」写到「毕业怎么配」：3 个成型阶段、4 段加点顺序、打法循环、优缺点、常见误区与可替换件
- 装备只引用名字，重量 / FP / 记忆格 / 获取位置全部从武器、护符、法术、骨灰四张原始表现查，不在流派数据里再抄一份数字
- 拿到手的不是「一套配装」而是「一条路线」：每个阶段写清楚先去哪张图、拿哪件东西、这一阶段的目标是什么
- 毕业配装只算武器与护符，给出的是「还剩多少负重留给护甲」—— 护甲人人穿得不一样，直接报档位会误导
- 详情页的「带进构筑器」把整套装备与属性塞进 `/build` 的 query，点进去就是自己的负重与需求缺口；回归检查逐套核对两边负重完全一致
- 与构筑器双向打通：构筑器选中的四套预设里，有三套能直接跳到流派库对应的完整路线

### 构筑器

- 选主手 / 副手武器 + 四个护符 + 记忆格法术，实时算出总负重、负重档位、属性需求缺口与 FP 消耗
- 负重按官方分段公式计算：耐力 20 → 64.1，99 → 160，负重类护符（众武护符系、黄金树的恩惠系）之间按乘法叠加
- 负重档位按「占最大负重百分比」判定：`<30%` 轻 / `30–69.9%` 中 / `70–99.9%` 重 / `≥100%` 超重，进度条上标了 30% 与 70% 两条刻度
- 给出「想进上一档需要多少耐力」：从 1 级往上逐级试到 99，和游戏里加耐力看负重条的行为一致，比反解分段函数更好核对
- 需求检查区分主手与副手：双手持握只对主手生效，力气按 1.5 倍（向下取整）计算；弓弩、盾牌、法杖、圣印记不支持双手持握，界面不显示该开关
- 负重护符不写死对照表，而是解析护符 `effect` 文案里的「装备重量上限 +19%」「负重 +5%」，以后补护符不用改代码
- 四套预设（月光剑法系 / 力敏出血 / 信仰战士 / 重装大盾），一键填入并附注意事项
- 整套构筑写入 URL query，可刷新、可分享、可后退；链接里出现失效 id 会自动清洗，不会凭空多出或少一件装备
- 预设选中后给一个入口，直接跳到流派库里这套的完整成型路线（预设只给数字，流派页给「怎么一步步走到这里」）

### 主题（底色 + 强调色，全站）

头部右上角有一个色点按钮，点开是两件事：**深色 / 浅色底色**，和**强调色**（7 个预设 + 取色器 + 十六进制输入框）。选择分别存 `localStorage`（`myplan.theme.mode` / `myplan.theme.accent`），刷新、换页都不丢；`main.js` 在挂载前先套一次，避免首屏闪一下默认色。URL 上加 `?theme=light` 可以强制某一套底色，方便把「浅色版」的链接直接发人。

#### 底色：两套 token，切一个属性

`<html data-theme="dark|light">` 一改，背景与文字四档整体翻过来：

| 变量 | 深色 | 浅色 | 用途 |
| --- | --- | --- | --- |
| `--bg` | `#121212` | `#f2efe7` | 页面底 |
| `--surface` | `#1a1a1a` | `#fbf9f3` | 卡片 / 面板 |
| `--surface-2` | `#202020` | `#eeeade` | 输入框、次级块 |
| `--surface-3` | `#262626` | `#e4dfd0` | 悬停、高亮块 |
| `--fg` → `--fg-4` | `#e5e3d8` → `#6b6555` | `#1e1c16` → `#6f6957` | 主 / 次 / 弱 / 更弱文字 |
| `--line` `--veil` `--shadow` | 亮色叠加 | 反向的暗色叠加 | 分隔线、微弱底、阴影 |

页面样式里**不再出现写死的深色或文字色**，全部走 token，所以切底色不需要动任何一个组件的样式。

#### 强调色：一个原色，其余派生

JS 只往 `<html>` 写一个 `--accent-raw`（用户选的原色），实际用的 `--accent` 由 CSS 决定：深色直接用原色，浅色压暗到 52%（鎏金在米白底上只有 2.1:1，压暗后才有可读性）。

| 变量 | 来源 | 用途 |
| --- | --- | --- |
| `--accent-raw` | 用户选择（默认 `#d4af37`） | 唯一由 JS 写入的值 |
| `--accent` | 深色 = 原色；浅色 = `color-mix(原色 52%, #1c1a14)` | 链接、按钮、标题强调、卡片描边 |
| `--accent-soft` / `--accent-line` | 同色 14% / 38% 透明 | 悬停底、标签底、强调态描边 |
| `--accent-ink` | 深色 `#141414`，浅色 `#fbf9f3` | 强调色当底时上面压的字 |
| `--el-color-primary` 及深浅档 | 从 `--accent` 派生 | Element Plus 的按钮、输入框、表格跟着变色 |

原有的板块色（影之刃零的朱红、旅游板块的墨绿）改成 `var(--accent)`，不再各自定死。

#### 语义色：换深浅但不换色相

红 / 绿 / 蓝 / 紫这些有含义的颜色不能跟着主题换色相，但浅底上又必须压深。统一写成：

```css
color: color-mix(in srgb, #8fa88a var(--tone-mix), var(--fg));
```

`--tone-mix` 在深色下是 `100%`（**就是原色本身，渲染零变化**），浅色下是 `40%`（压进深色前景，实测对比度从 1.7:1 提到 6:1）。

#### 这三步都是脚本做的，判据可量化

- **背景 / 文字**：按朴素亮度分档 —— 亮度 < 0.17 且饱和度 < 0.14 的算中性深色，按 `0.085 / 0.113 / 0.137` 三个阈值分到四档背景；亮度 ≥ 0.17、色相 18°–85°、饱和度 < 0.42 的算暖灰文字，按 `0.80 / 0.62 / 0.48` 分到四档文字。
- **强调色**：判据两条 —— 能不能用「强调色 × 透明度」在深底上还原（残差 ≤ 18/255），以及它是不是真的暖色系。只有第一条会把中性灰 `#383838`、墨绿 `#3f5237` 误判成强调色（数学上它们确实落在「金 → 深底」这条线上），所以淡档位（t < 0.45）额外要求色相 46°±22、饱和度 ≥ 0.12。
- **语义色**：饱和度 ≥ 0.06 且亮度 ≥ 0.28 的彩色一律套 `--tone-mix`；纯中性色不动。

默认深色主题下的实际观感：194 处纯强调色完全一致；按透明度档位换算的淡色，落在卡片底上平均差 6—9/255、页面底上 10—13/255，肉眼接近无差；个别中调描边色（如 `#8d7742`）偏 20/255 左右，属于「换成透明度写法必须付的代价」——换来的是这些描边能跟着主题色一起走。

背景和文字是在四档里各归各位，所以原本相邻的两档会被并成同一个值（比如 `#6f6a5a` 和 `#6b6555` 都进 `--fg-4`），差 4/255 以内，看不出来；换来的是这两个值都能跟着底色一起翻。

取色时实时算 WCAG 对比度：低于 4.5:1 提示「做小字偏淡」，低于 3:1 提示「几乎看不清，只适合做大色块」。浅色下按压暗后的实际颜色算，所以面板提示和真实渲染一致。

> 依赖 `color-mix()`，需要 Chrome 111+ / Safari 16.2+（2023 年后的浏览器）。老浏览器上这些声明会被忽略，颜色回落到继承值，不会崩版。
>
> 没做浏览器级自动深色（`prefers-color-scheme`）：这套站是给人手动选的，跟着系统走反而会出现「白天打开变浅色」的意外。要加也只是 `loadMode()` 里多读一个 media query 的事。

## 部署到 GitHub Pages

仓库已配置 `.github/workflows/deploy.yml`，push 到 `main` 即自动构建并发布。

本地手动构建子路径产物：

```bash
# Git Bash 需要 MSYS_NO_PATHCONV=1，否则 /static-site-demo/ 会被当成路径转换
MSYS_NO_PATHCONV=1 BASE_PATH=/static-site-demo/ npm run build
```

`vite.config.js` 读取 `BASE_PATH` 作为 `base`，路由使用 `import.meta.env.BASE_URL`。

### 版本号与部署确认

页脚右侧显示当前构建的 `v0.1.0 · 65f03d1 · 2026-10-28 05:25 UTC`，悬停可看每个值的含义。

| 值 | 来源 |
| --- | --- |
| 版本号 | `package.json` 的 `version` |
| 提交号 | CI 用 `GITHUB_SHA`，本地退回 `git rev-parse --short HEAD`，取不到就留空 |
| 构建时间 | 执行 `npm run build` 的时刻，统一 UTC（CI 构建机就是 UTC，避免和构建日志对不上） |

发版前把 `package.json` 的 `version` 往上调（`npm version patch` 也可以）。

部署完对一下线上页脚：

- 显示 **开发版** → 拿到的是 `npm run dev` 的页面，不是部署产物
- **提交号或时间没变** → 部署没生效或被缓存，先强制刷新，再核对 GitHub Actions 那次构建的 commit
- 时间变了但**提交号为空** → 构建环境里没有 git 信息（例如在无 `.git` 的目录里打包）

实现：`vite.config.js` 用 `define` 注入 `import.meta.env.APP_*`，`src/utils/version.js` 拼装，`src/components/BuildTag.vue` 渲染。注意必须走 `import.meta.env` 这条通道——Vite 在 dev 下只会把 `import.meta.env` 赋成对象，自定义的 `__APP_VERSION__` 之类标识符原样留着，运行时是 `undefined`。

### 深链接如何处理

这是 history 路由部署到静态托管的经典问题：直接访问 `/weapons/moonveil` 时服务器上没有对应文件，会返回 404。

处理方式分两层：

1. `scripts/gen-404.mjs` 在 `predev` / `prebuild` 阶段生成 `public/404.html`，把部署 `base` 写进脚本。404.html 先把真实路径存进 `sessionStorage`，再跳回站点根。
2. `src/router/index.js` 在创建 router 之前读回 `sessionStorage`，用 `history.replaceState` 把地址改回目标路径，用户感知不到中间跳转。

`public/404.html` 因此不入库（已加入 `.gitignore`），因为它依赖构建期的 `BASE_PATH`。

站内还有一个 catch-all 路由指向 `NotFoundView`，访问不存在的路径不会白屏。

## 架构

```
数据文件（src/data）→ utils 计算 / 筛选 → 视图渲染
                          ↑
              summary.js（构建期生成，首页专用）
```

几个约定：

1. **数据与视图分离**：每个模块的筛选、排序、匹配逻辑放在 `src/utils/*.js`，视图只负责渲染与交互；同类模块共用一个视图，差异通过注册表注入。
2. **首页统计独立**：`scripts/gen-summary.mjs` 在构建期从数据文件生成 `src/data/summary.js`，首页只读这几个数字，不引入完整数据集。
3. **列表分页**：`src/composables/usePagination.js` 接收「已筛选排序完成的完整列表」，输出分页切片。默认 20 条/页，另有 48 / 120 / 全部三档。
   - 之所以保留「全部」：分页后未展示的条目不在 DOM 里，浏览器 Ctrl+F 搜不到，容易被误认为数据缺失。结果条会提示当前处于哪种模式。
   - 筛选 / 排序任一变化都回到第 1 页（`resetToken` 指纹），结果变少时收敛越界页码。
4. **进度与收藏**：`useQuestProgress` / `useMainProgress` / `useWeaponFavorites` / `useCodexFavorites` 共用 `composables/progress.js` 里的 `createIdStore`，各占一个 `localStorage` key，互不干扰；同一个 key 只会创建一份 ref，天然跨组件共享。
5. **同一事实只存一份**：区域图鉴记「有哪些 BOSS」，BOSS 攻略记「怎么打」，追忆表记「能换什么」，三处靠 `${regionId}::${bossName}` 复合键与家族名对上，不复制内容。
6. **流派页不重复存数字**：流派数据只存「选什么、为什么、什么时候拿」，重量 / FP / 记忆格 / 获取位置全部从图鉴表现查，避免同一件装备的数值在库里存两份、改一处漏一处。
7. **长列表不铺 DOM**：构筑器的武器 / 护符 / 法术选择器用 480 条数据也只渲染前 24 条匹配结果（`components/ItemPicker.vue`），不用 `el-select` 全量铺开。
