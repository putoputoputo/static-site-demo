## 一、一句话定义

把「春节去北京玩」这件事，从「有哪些景点」推进到「哪天去哪几个、怎么走、要多久、花多少钱、必须提前准备什么」。

现在的站点能查游戏图鉴，但帮不上一次真实出行。这个板块要解决的是**决策**，不是**资料陈列**。

---

## 二、背景与目标

### 2.1 背景

- 站点现有三个板块：艾尔登法环攻略、影之刃零、摄影。站名叫「艾尔登法环攻略站」，但内容早就不止法环——加旅游之后这个名字彻底不成立，本次一并改为「我的计划」。
- 已确认的行程约束：**2027 年春节 2 月 5 日（除夕，周五）至 2 月 13 日（正月初八，周六）放假调休 9 天**，1 月 31 日、2 月 14 日上班（国务院办公厅 2026 年 11 月 5 日通知）。这是全部排期的硬边界。
- 用户已明确的三个硬约束：**必去故宫与长城**；**不是自驾，全程公共交通**；**电脑端为主，暂不做移动端适配**。

### 2.2 目标（可验收）

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G-1 | 打开站点 5 分钟内能定下一份 3 日行程 | 走一遍流程，从门户到拿到路线不超过 5 次点击 |
| G-2 | 每段通勤的时间与票价都能追溯来源 | 点击任一段路程可展开「数据来源 + 核对日期」 |
| G-3 | 每个景点的门票、预约、闭馆、证件条件一眼可见 | 详情页首屏即见条件表，无需滚动到第二屏 |
| G-4 | 地图上一眼看出景点相对位置与所选路线走向 | 选完路线，图上路径高亮，点位与顺序编号对应 |
| G-5 | 不出现自驾方案 | 全站文案与算法均不产生驾车路线 |

### 2.3 非目标

本期不做：移动端适配、账号体系、云端同步、支付与预订跳转、实时公交到站、多城市扩展。

## 三、用户与场景

### 3.1 用户

单人出游或 2—3 人小团，具备基本自助游能力，愿意换乘地铁但不愿折腾长途汽车。对北京不熟，知道故宫和长城是必去，但不知道它们之间怎么串、一天能塞几个、春节要注意什么。

### 3.2 三个核心场景

| 场景 | 时机 | 用户在想什么 | 板块要给什么 |
|---|---|---|---|
| S-1 看图定取舍 | 出发前 1—2 个月 | 「北京这些景点都在哪，哪几个离得近」 | 一张位置图 + 必去卡 + 片区划分 |
| S-2 排行程 | 出发前 2—4 周 | 「我住这，想去这几个，怎么排才不折腾，一天够不够」 | 选起终点 → 多条候选路线，带时间与花费 |
| S-3 核对条件 | 出发前 1 周内 | 「故宫到底要不要预约，几号闭馆，长城怎么去」 | 条件卡 + 春节特别提示 |

S-2 是核心，S-1 与 S-3 是它的前后支撑。三者共用同一份景点数据，不做两套。

### 4.4 行程长度与节奏：交给算法给方案，不让用户先猜

你回答「玩几天」「一天几个景点」都是「不确定，按路线来」，所以规划器不要求先填这两个数。改成：**输入起点与终点，输出三档不同长度的候选路线，各自标出需要几天、每天几个点、每天在途多久**，由你按体力挑。

| 档位 | 景点数 | 通常需要 | 适合 |
|---|---|---|---|
| 紧凑 | 3—4 个 | 1 天 | 只想覆盖核心，市区不挪窝 |
| 标准 | 5—7 个 | 2 天 | 建议默认选这档 |
| 完整 | 8—10 个 | 3 天 | 假期富余，覆盖两个方向 |

这条替代了原计划里的「天数输入框」，少一个必填项，也避免用户填错之后再返工。

### 4.5 过夜点怎么定（住处未定时的处理）

你还没定住处，而不定住处就没法算「每天几点回酒店」。处理方式是**反推**：路线按天切分后，每天最后一个景点就是当天落脚区域，页面给一句「第 1 晚建议住 XX 附近（最近地铁站 XX，周边酒店密集）」。

好处是不需要你先定住处就能出完整行程，而且给出的住宿建议是跟着动线走的，比先定住处再硬凑路线合理。等住处定了，可以按住处重新跑一次，只影响每天首尾两段。

## 六、核心功能设计

### 6.1 景点数据模型

```js
{
  id: 'forbidden-city',
  name: '故宫博物院',
  alias: ['紫禁城'],
  district: '东城区',
  area: 'gugong',           // 片区，用于聚类与地图分组
  lat: 39.9163, lng: 116.3972,
  ticket: {
    peak: 60, peakNote: '4月1日—10月31日',
    offPeak: 40, offPeakNote: '11月1日—次年3月31日',
    extra: [{ name: '珍宝馆', price: 10 }, { name: '钟表馆', price: 10 }],
    free: null,
  },
  booking: {
    required: true,
    channel: '「故宫博物院」微信小程序',
    leadDays: 7,            // 最早可于参观 7 日前 20:00 预订
    note: '未授权任何第三方代理，每日限流 4 万人',
  },
  hours: {
    peak: '08:30—17:00（16:00 停止入馆）',
    offPeak: '08:30—16:30（15:30 停止入馆）',
    closed: '除法定节假日外全年周一闭馆',
    closedWeekday: 1,
  },
  durationMin: 240,          // 建议停留，分钟
  bestTime: '开馆即入，或 14:00 后',
  entry: '午门进、神武门出，单向参观',
  access: [{ type: 'metro', text: '地铁 1 号线天安门东站 B 口，步行约 900 米' }],
  conditions: ['刷身份证检票', '安检，禁带自拍杆、无人机', '需实名，证件与预约一致'],
  tips: ['珍宝馆与钟表馆需单独购票', '院内餐饮少，建议自带水'],
  source: { url: 'https://ticket.dpm.org.cn', checkedAt: '2026-11-16' },
}
```

字段设计原则：

- **每条数据要么有 `source`，要么标 `pending: true`**，不允许两个都空。这条会用回归脚本卡住。
- `durationMin` 是路线算法的时间预算输入，不是给人看的文案。
- `closedWeekday` 让算法能自动避开闭馆日，不靠人工记。
- `leadDays` 用于「出发前核对」提醒，倒推哪天必须下单。

### 6.2 景点分布图：方案对比

| 维度 | 方案 A：自绘 SVG 示意地图 | 方案 B：高德 / 腾讯地图 JS API |
|---|---|---|
| 外部依赖 | 无 | 需要 key（申请 + 实名 + 配额） |
| key 泄露风险 | 无 | 有，纯前端必然暴露 |
| 离线可用 | 可用 | 不可用 |
| 真实底图 | 无，只画简化的环路与水系轮廓 | 有 |
| 样式贴合暗色主题 | 完全可控 | 需覆盖大量默认样式 |
| 路线高亮 | 完全自由 | 受限于覆盖物 API |
| 开发量 | 约 1 天 | 约 2 天，另加 key 申请与备案 |
| 长期成本 | 零 | 有配额与key轮换成本 |

**推荐 A**。理由：需求原话是「标注各个景区的大概位置」，不是导航；14 个点在 40×30 公里的范围内，示意图完全够用。摄影板块已经吃过一次 key 的亏（AI key 改成用户自填），旅游不该再引入一个必须联网的外部服务。

实现要点：

- 经纬度 → 画布用等距圆柱投影，按北京纬度取 cos(39.9°) ≈ 0.767 做经度缩放，避免东西向被压扁
- 底图只画三样：五环内简化环路、永定河与昆明湖轮廓、片区淡色块。不画街区，画多了反而看不清点位
- 点位用数字圆标 + 名称标签，同一片区标签自动错位避免重叠
- 选完路线后，路径按顺序连折线，线段粗细表示通勤时长，叠加箭头方向

### 6.3 路线规划：方案对比

| 维度 | 方案 A：只做预置经典路线 | 方案 B：起终点 + 自动组合 | 方案 C：调外部路径规划 API |
|---|---|---|---|
| 满足「选出发地和目的地」 | 不满足 | 满足 | 满足 |
| 通勤时间准确度 | 手填，准 | 矩阵计算，较准 | 最准，含实时路况 |
| 外部依赖 | 无 | 无 | 需 key，且有调用配额 |
| 组合灵活性 | 固定 3 条 | 按输入动态生成 | 高 |
| 开发量 | 0.5 天 | 2 天 | 3 天 + key |

**推荐 B + A 混合**：算法生成候选，预置经典路线作为兜底与对照。C 不做——公交换乘的真实数据拿不到稳定免费额度，且纯前端暴露 key。

算法设计（关键，决定体验好坏）：

**第一步：抽象「地点」**。起点和终点既可能是景点，也可能是我住的酒店、北京南站。所以统一抽象为 `place`：景点（来自景点库）或自定义地点（名称 + 经纬度或所属地铁站）。这一步不做，规划器就只能传景点，用户最常见的「从我住的酒店出发」就表达不出来。

**第一步：起点与终点都从景点库里选**。已确认按「景点→景点」串联，不做自定义地点输入。取舍要写明白：「住处→起点」「终点→住处」这两段不参与计算，页面用一行提示交代两端最近的地铁站，并注明这两段需自行安排。这样算法只在景点之间连线，边界干净，也不用先定住处。

**第二步：片区聚类**。18 个景点分布在 7 个片区（古北水镇 `remote` 不参与）。先按片区聚合，再在片区内部排序，组合空间从 P(18,k) 降到 P(7,k) 量级，浏览器里瞬间算完。

**第三步：长城按走向自动选段**。八达岭在西北（延庆），慕田峪在东北（怀柔），方向相反。做法是算路线其余景点的经纬度质心，取「质心到两段长城的距离差」，近的那段作为路线里的长城站，另一段在同页给对照（含怎么去、票价、时长）。这样不用预设，也不会出现「去东北的路线却绕西北爬长城」。

**第四步：硬约束**（不满足直接排除）

1. 故宫必须出现；长城默认必须出现（可一键关闭），且八达岭 / 慕田峪择一
2. 长城单独占一天：市区往返单程 1.5—2 小时，加登城 3 小时，一天塞不下第二个景点
3. 周一闭馆的景点不得排在周一（故宫 `closedWeekday: 1`）
4. 单日景点数 2—4 个自适应：片区越集中塞得越多，跨片区就自动减
5. 每天结束点即当晚落脚区域，次日从该点继续，不回头

**第五步：打分排序**

```
score = 100
      − 跨片区次数 × 12        // 来回穿城是最烦的
      − 每日超时惩罚 × 15      // 当天总时长 > 9 小时开始扣
      − 通勤总时长 / 30        // 分钟折算
      − 折返惩罚 × 20          // 路线自相交
      + 同片区相邻奖励 × 8
```

取分数最高的 3 条，并且**刻意保留差异**：至少一条「少走路、景点少」的轻松版，至少一条「多覆盖」的紧凑版，而不是三条几乎一样的路线。

**第六步：输出**

```
第 1 天（2 月 6 日 · 周六）
  09:00  故宫博物院        停留 4h     门票 40
  13:30  → 景山公园        地铁 1 号线 2 站 · 12 分钟 · 3 元
  13:45  景山公园          停留 1.5h   门票 2
  ...
  当天合计：步行 4.2km · 地铁 3 段 · 交通 9 元 · 门票 42 元 · 在途 6.5h
  夜间建议：住南锣鼓巷一带（最近 6 号线南锣鼓巷站，次日去什刹海步行可达）
```

### 6.4 通勤数据：怎么算才不瞎编

分三级，越靠近数据源越准：

| 层级 | 覆盖范围 | 数据来源 | 精度 |
|---|---|---|---|
| L1 片区间 | 如 故宫片 ↔ 长城片 | 手填，来自官方交通指南与公开攻略，标来源 | 给区间（90—120 分钟），不给单值 |
| L2 同片区内 | 如 故宫 → 景山 | 按直线距离 × 步行绕行系数 1.35 估算，或地铁 1—2 站固定值 | 标「估算」 |
| L3 长城专线 | 市区 → 八达岭 | 四条固定方案并列，见下表 | 来自官方与铁路公告 |

市区到八达岭的四条路（已在计划书内固定，页面直接给对比表）：

| 长城巴士直通车 | 国家图书馆地铁站 C 口 | 约 90 分钟 | 往返 80 元（不含门票） | 班次随季节调整，需确认当年是否开行 |

- **所有估算值在页面上必须带「估算」标记**，不能和官网数据混在一起显示

### 9.2 M4 落地时改变的三处设计

计划书原来的设想是「片区聚类 → 打包成天」，实际做下来改了三处：

**① 装箱按「当天时长」而不是「片区」**。原计划按片区聚合，实施时发现片区大小差太多：故宫片 6 个点塞不进一天，朝阳片只有 798 一个点却要独占一天，会出现「上午 11 点就结束」的空转。改成按时长装箱，片区只决定先后顺序。

**② 起点终点不参与装箱**。最初把起终点当普通景点一起装，结果是「终点被装到第一天中间，后面还多出一天」。改成装完中间点再把起终点钉进首尾，第一天要额外装起点时容量提前扣掉。

**③ 周一闭馆是「对调行程」而不是「对调日期」**。第一版交换日期，页面出现「第 2 天 2/8、第 3 天 2/7」的日期倒流。改成各自保留日期、交换行程内容。

### 9.3 高德地图：最终选择 URI 外链，不嵌 JS 地图

原计划用自绘 SVG，用户提出「高德更好的话也可以改用」。结论是**用高德，但不嵌图**：

| 方案 | 结论 | 理由 |
|---|---|---|
| 高德 JS API 嵌地图 | 未采用 | 需要注册「Web 端 (JS API)」key + 安全密钥，且要联网；而自绘 SVG 离线可看、零请求，对「标注大概位置」这个需求已经够用 |
| 高德 URI 外链 | **采用** | `uri.amap.com` 不需要 key，点开就是高德 App / 网页版，能直接导航——比嵌一张不能交互的地图更实用 |
| 坐标系 | **做了转换** | 项目坐标是 WGS-84，高德是 GCJ-02，直接传会偏 300—500 米。`src/utils/geo.js` 实现标准转换后再拼链接 |

留了升级口子：`geo.js` 里的 `AMAP_JS_KEY` 填上就能接 JS 地图，组件的降级逻辑已经按「有 key 用高德、没 key 用 SVG」的形态写好位置。

### 9.4 起终点从「只能选景点」放开到「可打字搜地点」

用户反馈「没看到可以自定义出发地和目的地的地方，至少能自由选择」。原因有两层：

1. **入口太深**：规划器藏在顶部「旅游 · 路线」下拉里，首页只有一个页脚链接 → 首页第一屏加了起终点快选
2. **只能从下拉里点**：18 个景点里没有机场和火车站，而游客的实际出发地就是这些 → 起终点改为**可打字的选择器**，候选池扩到「17 个景点 + 9 个交通枢纽」

| 改动 | 落地 |
|---|---|
| 候选池 | 新增 `src/data/travel/hubs.js`（9 个枢纽：北京南/西/站、朝阳、清河、首都机场、大兴机场、德胜门、东直门），坐标为 WGS-84，带出处 |
| 选择器 | 新增 `src/components/travel/PlacePicker.vue`：输入即筛、上下键移动、回车选中、失焦还原，支持别名（搜「紫禁城」出故宫）与缩写（搜「南站」出北京南站） |
| 算法 | 枢纽不进景点序列：作 `origin`（第一天第一段的起点）与 `terminus`（最后一天补「最后一站 → 枢纽」）。枢纽无停留时长，装箱容量按 0 处理 |
| 地图 | 枢纽画成方形点，只在它参与的那一天显示（第一天画出发点、最后一天画终点），避免常驻标签压住什刹海的密集点位 |
| 通勤 | 枢纽 ↔ 景点按「直线 × 1.3 ÷ 速度 + 进出站开销」估：机场线 900 米/分钟、机场加 25 分钟、火车站加 8 分钟；机场按机场线票价（25 / 35 元）而非地铁里程票 |

**曾记为未做、现已补上**：任意门牌地址（酒店、某个小区）。通过高德 Web 服务 `v3/place/text` 做 POI 联想，用户输入什么地点都能当选起终点；这类地点没有停留时长与门票概念，按 0 处理，只当端点锚。

### 9.5 接入高德 Web 服务（任意地点 + 真实公交方案）

用户提供了高德 key。落地方式：**直连 `restapi.amap.com`，不引 JS SDK**。

| 事项 | 结论 |
|---|---|
| 为什么不用 JS API | restapi 响应头是 `Access-Control-Allow-Origin: *`，浏览器可直连；不用塞 300KB SDK，也不用 AMap 的容器与事件体系。我们只要「地点搜索 + 路线规划」两个接口 |
| key 类型 | 必须是**「Web 服务」**平台的 key。JS API 的 key 调 restapi 返回 `USERKEY_PLAT_NOMATCH (10009)`；带 `platform=JS` 又会要安全密钥 `INVALID_USER_SCODE (10008)`。用户首个 key 正是 JS API 平台的，所以页面在报错里直说「去新建 Web 服务 key」 |
| key 存放 | localStorage（`myplan.amap.webkey.v2`），代码里放一个默认值。换 key 不用重新构建，页面底部有输入框 + 「测试」按钮；存了自填 key 时多一个「用默认 key」把 localStorage 清掉。版本号取 v2 是为了让之前存过的坏 key 失效 |
| 坐标 | 高德返回 GCJ-02，进状态前先 `gcj02ToWgs84` 转回 WGS-84（单次迭代，残差 < 1 米）；调高德接口时再转回去。转换只发生在边界上 |
| 地点搜索 | `v3/place/text`，`city=北京` + `citylimit=true`。输入 350ms 防抖（中文输入法一个字一次 input），结果作为独立分组「高德搜索 · 任意地点」出现在本地库之后 |
| 路线规划 | `v3/direction/transit/integrated`，取前 3 个方案，展示总时长、公里数、换乘次数、步行米数、每段线路的上下车站与站数 |
| 任意地点当端点 | 与枢纽同一套机制：`isCustom` 标记，不进景点序列，只当 `origin` / `terminus` |

**踩坑**：`orderDay` 的 `firstPin` 会把端点钉进景点序列——枢纽上踩过一次，自定义地点又踩了一次。现在统一用 `isAnchor()` 判断（枢纽或自定义），不再各写各的。

**实测记录**（默认 key，2026-11-16）：`place/text` 搜「全季酒店 王府井」首条命中门店；`北京南站 → 首都机场 T3` 返回 3 个方案，最快 106 分 / 41.7 km / 9 元 / 换乘 2 次 / 步行 1134 米；`direction/driving` 同路线 80 分 / 35 km。搜索与公交两条链路都是真调通的，不是只有错误分支能跑。

### 12.1 三个由此产生的取舍（需要你知道）

1. **两段通勤不在计算内**：选了「故宫→颐和园」，算法不算你从住处怎么到故宫。路线首尾各给一行「起点最近地铁：1 号线天安门东站」，剩下的自行安排。这是「景点→景点」方案的必然缺口，不假装能算。
2. **多天行程的过夜点靠反推**：住处未定时，第 N 天最后停在哪，就建议住哪。等你定了住处可以按住处重跑，只影响每天首尾两段。
3. **古北水镇不进主算法**：距市区约 140 公里、要过夜，硬塞进市区路线会把整天空耗在路上。只在长城片区作为延伸选项单独列出。

### 12.2 仍未定、但不阻塞开工

春节 9 天里具体用哪几天、同行几人、预算上限。这三项不影响算法与页面结构，页面先按「单人、淡季票价、9 天窗口全开」处理，确定后改一处配置即可。
